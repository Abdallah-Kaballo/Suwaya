Specification & methodology

This page is an orientation layer, not a substitute for source code. If documentation and implementation differ, inspect the actual code and tests and record the discrepancy rather than hiding it.

The published document identifies the model as Schedule Model V2 and describes a Flutter-independent Dart package. Performance or test-coverage statements in documentation should be treated as verifiable claims, not independent audit results.

Model definition

  • The cycle begins at the selected Maghrib anchor and ends at the next Maghrib.
  • It contains 24 virtual Suwayas: 12 in the night phase and 12 in the day phase.
  • Each Suwaya is 60 virtual minutes or 3,600 virtual seconds, not necessarily 60 civil minutes.
  • Units are allocated across seven contiguous periods: four night periods and three day periods, based on engine-generated anchors.
  • The allocation must sum to 24, and each period end must equal the next period start without gaps or overlap.
Flow speed = 3600 ÷ physical duration of one Suwaya in seconds

Anchors and inputs

According to the published specification, results depend on coordinates, date/instant, time-zone identifier, Fajr/Isha calculation method, madhab for Asr, high-latitude rules, and allowed user adjustments.

The document lists multiple calculation methods, high-latitude rules named middleOfTheNight, seventhOfTheNight, and twilightAngle, and manual offsets from −30 to +30 minutes. It states that sunrise is excluded from manual offsets and that pure astronomical sunset is kept separate from adjusted Maghrib when the former is used for Hijri date rollover.

These describe the declared methodology; each rule should be checked against the relevant source files, especially after version changes.

Numerical mapping

Elapsed physical time within a period is mapped to a virtual position by its fraction of the period's physical duration. The reverse mapping converts a requested virtual fraction back to a physical offset. Durations should be computed from UTC instants, with local time-zone projection used for display, to avoid errors around civil-clock changes.

A core test requirement is round-trip consistency within the documented precision, monotonicity, and keeping resolved instants within period boundaries.

Exceptions and declared limitations

  • High latitudes: some twilight anchors may fail during midnight sun or polar night. The specification describes synthetic or projected anchors. These estimates must not be presented as direct local observations.
  • Daylight saving: physical durations should be computed in UTC; a local civil day must not be assumed to always contain 24 hours.
  • Madhab and calculation method: results are not a single absolute value and can differ by configuration.
  • Religious and astronomical validity: successful software arithmetic does not by itself establish jurisprudential correctness or observational agreement; a reference and comparison criterion are needed.
  • Allocation: assigning unit counts to intervals is a software convention. Latitude bands and seasonal transitions require explicit documentation and boundary tests.

Audit notes that should remain visible

Detailed documentation can contain inconsistencies in latitude thresholds, allocation tables, or anchor naming. For any release, compare these claims with the implementation and tests and record discrepancies as open issues. Do not present a fixed number as a normative fact unless it matches the current code.

This page does not claim standards-body adoption or independent audit. Its purpose is to make assumptions inspectable and source review easier.
